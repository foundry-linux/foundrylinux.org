## Why — and it validates the one-commit pin rather than undermining it

The submodule inventory explains it exactly. protobuf was fetched at `edaa823d…`, but there are **no nested `3rdparty/protobuf/protobuf/third_party/*` entries** in the inventory — modern protobuf *dropped* its abseil git submodule and pulls abseil with `FetchContent` from GitHub at configure time instead. So no amount of submodule recursion could have supplied it; the AUR's per-submodule tarball table would have hit precisely the same wall.

Notably, debhelper had already set `FETCHCONTENT_FULLY_DISCONNECTED=ON` — Debian's own guard against exactly this — so the build refused to fetch. That is the correct behaviour catching a real problem.

## Fix

Ubuntu 26.04 ships `libabsl-dev 20260107.0-4`, and protobuf's `abseil-cpp.cmake` tries `find_package(absl CONFIG)` *before* falling back to download. So:

- `libabsl-dev` added to `Build-Depends` and `build.sh`'s apt list.
- `-Dprotobuf_LOCAL_DEPENDENCIES_ONLY=ON` added to `debian/rules` — not strictly required once absl is installed, but it converts "silently try to download from GitHub" into a hard error, which is the policy we want enforced structurally rather than by luck.

## The two configure failures, and why neither is a shape change

Both are exactly the class of problem that only a real build surfaces, and both have structural fixes rather than workarounds:

**1. protobuf → abseil.** Modern protobuf dropped abseil as a git submodule and `FetchContent`s it from GitHub at configure time. debhelper's `FETCHCONTENT_FULLY_DISCONNECTED=ON` correctly refused. Fixed with `libabsl-dev` (26.04 ships `20260107.0-4`) plus `-Dprotobuf_LOCAL_DEPENDENCIES_ONLY=ON`, which turns any future silent download attempt into a hard error.

**2. LTO.** Ubuntu 26.04 puts `-flto` in the default build flags; RPCS3 refuses to configure when it sees one:

```
CMake Error at CMakeLists.txt:118 (message):
  RPCS3 doesn't support building with LTO, use -DDISABLE_LTO=TRUE to
  force-disable it
```

I did **not** take upstream's suggested `-DDISABLE_LTO=TRUE`. That option only regex-strips `-flto` out of `CMAKE_C_FLAGS`/`CMAKE_CXX_FLAGS` and leaves it sitting in `LDFLAGS`, which is how you get a link-time surprise later. Clearing the feature properly through dpkg-buildflags — `DEB_BUILD_MAINT_OPTIONS = hardening=+all optimize=-lto` — removes it from compiler and linker flags alike. Hardening (PIE, relro, bindnow, stack-protector, fortify) is untouched, which verification step 5 will confirm.

Worth noting the abseil finding retroactively strengthens the design call you made: the AUR's 18-tarball submodule table would have hit the identical wall, because no amount of submodule recursion can supply a dependency that upstream fetches with `FetchContent` instead of vendoring.
